# 将来構想: 日・韓・英 UGC 自動翻訳基盤

## 位置づけ

この文書は、ユーザーが作成・公開した Tier 表を日本語・韓国語・英語へ非同期翻訳し、各言語圏で閲覧・検索できるようにする将来構想を記録する設計メモである。

現時点では自動翻訳を実装しない。翻訳 API、Cloud Functions、Cloud Scheduler、Firestore schema、UI、URL、SEO の変更も行わない。本構想を理由に現在の実装を過剰設計せず、今後の変更で拡張可能性を不用意に失わないための判断材料として扱う。

## 目的

目的は単なる「翻訳ボタン」の提供ではない。1つの国・言語で作られたユーザー生成 Tier 表を、他言語圏でも再利用可能なコンテンツ資産にすることである。

将来構築するパイプラインの基本思想は次のとおりとする。

```text
公開
  → モデレーション
  → 需要判定
  → 非同期翻訳
  → 多言語結果の保存・再利用
  → 多言語表示・検索・SEO
```

これにより、日本・韓国・英語圏の UGC を相互に流通させる循環を目指す。

## 想定パイプライン

```text
ユーザーが Tier 表を作成・公開
  → Firestore に原文を保存
  → モデレーション
  → approved
  → translationStatus = pending
  → 夜間バッチが対象を抽出
  → Translation Provider を呼び出す
  → ja / ko / en の翻訳結果を Firestore に保存
  → 各言語版の表示・検索・SEOで再利用
```

アクセスのたびにリアルタイム翻訳する方式は原則採用しない。一度生成した翻訳を保存し、同じ原文・翻訳バージョンに対して再利用する方式を第一候補とする。

## 翻訳対象と対象外

将来の翻訳対象候補:

- Tier 表タイトル
- Tier 表説明文
- ユーザーが設定した Tier ランク名
- ユーザー入力による項目名
- その他、公開ページ上のユーザー生成テキスト

対象外:

- ボタン、ナビゲーション、エラー等の固定 UI 文言

固定 UI 文言は、引き続き既存の i18n / localization で管理する。AI 翻訳結果とアプリの固定文言を混在させない。

## UI locale と原文言語を分離する

次の2つは別の概念として扱う。

- ユーザーがアプリを操作するときの UI locale
- Tier 表のユーザー生成テキストが書かれた原文言語

UI が日本語だから投稿原文も日本語、という推論に依存しない。今後のモデル・Repository・検索・URL設計でも、両者を同一フィールドや暗黙の前提にまとめない。

## 固有名詞の翻訳方針

Tier 表には、アニメ・漫画・ゲームのタイトル、キャラクター名、アーティスト名、人物名、商品名などの固有名詞が多い。将来の翻訳処理では単純な直訳を避け、次の優先順位を採用する。

1. 公式の現地語表記が明確なら公式表記を優先する
2. 確信できない場合は勝手に意訳しない
3. 不明な固有名詞は原文維持を許可する
4. Tier 表として自然なタイトルになるよう文脈を考慮する

翻訳 Provider のプロンプトまたはポリシーは、この規則を差し替え可能な形で管理する。

## 翻訳対象の選別と優先順位

全投稿を無条件に翻訳しない。最低限、次の条件をすべて満たす投稿を候補とする。

```text
isPublic == true
moderationStatus == approved
translationStatus == pending
```

さらにコストを制御するため、将来は `viewCount`、参加者数、いいね数、作成からの経過時間などによる需要判定を追加できるようにする。

匿名投稿も公開可能とする現在の思想を維持する。ただし、匿名かログイン済みかだけで対象を決めず、コンテンツ需要を優先する設計を検討する。

- 匿名投稿かつ閲覧実績なし: 翻訳優先度を下げられる
- 匿名投稿でも一定以上閲覧されている: 通常投稿と同様に翻訳対象にできる

## 将来のデータ構造候補

以下は概念例であり、現時点の Firestore schema へ追加しない。

```yaml
originalLanguage: "ja"

translations:
  ja:
    title: "..."
    description: "..."
  ko:
    title: "..."
    description: "..."
  en:
    title: "..."
    description: "..."

translationStatus: "completed"
translationProvider: "claude"
translationVersion: 1
translatedAt: timestamp
```

想定する状態:

```text
none
pending
processing
completed
failed
```

実装時には、翻訳を Topic 文書へ埋め込む方式と翻訳専用サブコレクションへ分離する方式について、ドキュメントサイズ、クエリ、権限、更新頻度、SEO生成処理を比較して決定する。

## 原文編集と再翻訳

原文が編集された場合、古い翻訳を有効なまま使用し続けない。

```text
ユーザーが原文を編集
  → translationVersion を更新
  → translationStatus = pending
  → 古い翻訳を stale として扱う
  → 夜間バッチで再翻訳
```

翻訳ジョブは Topic ID だけでなく原文または翻訳バージョンを確認し、処理中に原文が更新された場合に古い結果で上書きしない、冪等な設計とする。

## Provider を交換可能にする

現時点では翻訳事業者を固定しない。候補には Claude API、Gemini API、Papago Translation API、その他の翻訳サービスがある。

将来の呼び出し経路は次を原則とする。

```text
Flutter
  → Firestore
  → Cloud Functions / Scheduler
  → Translation Provider
```

- Flutter クライアントから翻訳 API を直接呼び出さない
- Provider 固有のリクエスト・レスポンスをドメインモデルから分離する
- API キーは Secret Manager で管理する
- Provider 名、翻訳バージョン、処理日時を記録し、再生成と移行を可能にする
- 一部失敗、タイムアウト、レート制限へ再試行可能な設計にする

## 夜間バッチを第一候補とする理由

- API コストを制御しやすい
- 同一投稿の重複翻訳を防ぎやすい
- 閲覧時の表示速度へ影響を与えない
- モデレーション完了後だけ翻訳できる
- 失敗時の再試行と監視を分離できる
- 人気投稿のみ処理するなどの最適化が可能

将来的には Cloud Scheduler と Cloud Functions 等を候補とするが、実装時点のサービス仕様、料金、実行時間制限を再評価する。

## 多言語URLとSEO

同一 Tier 表について、将来的に次のような言語別 URL を持つ可能性を考慮する。

```text
/ja/topic/{id}
/ko/topic/{id}
/en/topic/{id}
```

実装時には各言語について以下を整合させる。

- `hreflang`
- canonical URL
- HTML `title` と `description`
- OGP
- sitemap
- 検索エンジン向けHTML
- 翻訳未完了・失敗・原文更新直後のフォールバック

目標とする循環:

```text
日本語圏の投稿 → 韓国語・英語で検索流入
韓国語圏の投稿 → 日本語・英語で検索流入
英語圏の投稿   → 日本語・韓国語で検索流入
```

## 今後の実装で守る制約

- `language` を日本語固定にしない
- Tier データ構造を日本語前提にしない
- URLを日本語だけに強く依存させない
- `title` 等を将来翻訳データへ拡張不能な形にしない
- UI locale とコンテンツ原文言語を同一視しない
- 翻訳前の原文を失わない
- モデレーション前や非公開の投稿を翻訳対象にしない
- 翻訳結果を原文として再翻訳しない

## 現時点で実施しないこと

- Claude API、Gemini API、Papago API等の導入
- 翻訳用 Cloud Function の作成
- Cloud Scheduler の設定
- Firestore schema の変更
- 翻訳UIの追加
- URL変更
- SEO構造変更

この文書は将来の設計判断を補助するものであり、現在の挙動や公開データモデルを変更するものではない。
