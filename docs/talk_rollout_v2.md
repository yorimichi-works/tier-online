# 投稿 v2 の切替・保持・アカウント削除

この文書は承認後の手順書であり、本番操作の実施記録ではない。
このタスクでは本番データ削除、ルール・インデックス適用、デプロイ、ストア提出を一切していない。
依存パッケージは更新していない。アプリのリリース番号だけを `0.1.0+2` にした。

## 互換ゲートとバージョン判定

| クライアント | 宣言 | 動作 |
| --- | --- | --- |
| 従来版（`0.1.0+1`、宣言なし） | protocol/build なし | 埋め込み返信・過去の評価は閲覧可。親全体の書き戻しは拒否 |
| 本変更（`0.1.0+2`） | `clientProtocolVersion: 2`, `clientBuild: 2` | ゲートが開いていれば本人の投稿・返信・票を書き込める |
| 必須 build 未満、未知の protocol | 宣言不適合 | 更新が必要。既存データは消さない |

`TalkClientVersion.build` と pubspec の build 番号の一致をテストする。
この宣言はクライアントの自己申告であり、本人確認やアプリ認証の代わりに使わない。
宣言を偽装しても、作者 UID・トピック公開範囲・変更可能フィールドの検査を通る必要がある。
Firestore の部分 update は保存済みのバージョン情報を引き継ぐ場合があるが、本文の作者認可は常に適用される。

ゲートは既存の信頼済み Admin SDK 運用で管理する `clientPolicies/talks`。
クライアントにはこの文書の read だけを許し、create/update/delete をすべて拒否する。
新しい IAM 権限・サーバー認証情報は必要ない。

```json
{
  "writesEnabled": false,
  "readProtocolVersion": 2,
  "minProtocolVersion": 2,
  "minClientBuild": 2
}
```

未作成・型不正・停止中は書き込みを拒否する。`minClientBuild` を上げると旧 build を停止できる。
クライアントも書き込み前にサーバーから確認し、ルールはコミット時に再検査する。
停止中でも読み取りルールは維持され、v2 の返信・評価も引き続き表示できる。
新クライアントが旧バックエンドを読む場合、policy read の permission-denied を検出して
旧埋め込みデータの読み取りに限定し、書き込みは停止する。

## 承認後の段階的な切替

1. **保全と準備。** 本番とは別の検証環境で本タスクのテストを実行し、既存バックアップ手順と
   切替時間を確認する。旧データの作者 UID や評価の内訳を補完するスクリプトは使わない。
2. **書き込み停止。** 承認された本番作業として新ルールを適用する。policy 未作成の時点から
   書き込みは停止する。`config/talk-write-policy.v2.json` は停止状態の雛形であり、自動適用されない。
3. **既存削除機能と index。** `deleteAccountData` を含む既存 Functions の更新と、
   `firestore.indexes.json` の collection-group index を承認された手順で反映する。
   `talks.authorUserId` / `talks.replyAuthorIds` / `replies.authorUserId` / `reactions.userId` が
   利用可能になったことを確認する。確認前にゲートを開けない。
4. **読み取りを維持してクライアント更新。** policy を上の停止状態で用意し、build 2 を配布する。
   Web の再読み込み・既存 Service Worker とキャッシュの更新を確認する。ネイティブ版の提出・公開は別承認。
   更新前の Web タブや旧ネイティブ版が残っても、親全体の書き戻しは拒否される。
5. **検証環境で受入確認。** 公開/非公開、匿名/未確認メール、旧返信と新返信の同時表示、
   過去の評価数の保持、返信失敗後の再送、2端末の票、fixture のアカウント削除を確認する。
6. **開放。** 本人が反映を承認し、上記の準備が完了した後だけ `writesEnabled: true` とする。
   ルールを弱めて旧クライアントを許可する互換経路は作らない。

障害時は `writesEnabled: false` に戻す。新返信・評価文書も旧埋め込みデータも削除せず、
build 2 の読み取りを維持して修正版を用意する。脆弱な旧ルールへの復元は切戻し手段にしない。

## 未送信データと複数端末

- v2 の返信は、送信前に `pendingTalkReplies.v2.{uid}.{topicId}` へ返信 ID・本文・親 ID を保存する。
  permission-denied のような確定した失敗でもキューを消さず、UI は「端末保存済み・再試行」を示す。
  次の操作、または再試行ボタンから同じ UID だけが同じ ID で再送する。再起動後も復元する。
  クラウド優先マージで親投稿が置換されても、未送信返信はこの独立したキューから表示を復元する。
  ローカルのキュー追加・状態更新・成功 ID の除去だけを短い保存ロックで直列化し、通信の直列化とは分ける。
  先行通信が保留でも後続返信は先に保存される。送信成功時に古いキュー全体を上書きしないため、
  先行通信の応答によって後から保存した返信が消えることも防ぐ。
- 返信ごとの送信失敗は本文を残して記録し、無関係な投稿・返信・評価を中止しない。
  サーバー読み取りで親投稿の欠落を確認できた返信は `parent-unavailable` として自動送信から隔離する。
  明示的な「再試行」は隔離項目も一度試し、まだ親がなければ本文を保持したまま失敗を返す。
  読み取り拒否だけから削除を推測せず、通常の認可失敗も項目単位で保持する。
- 別 UID に切り替えても元 UID のキューを送信しない。投稿本文や作者情報を再送のために書き戻さない。
  保存キーの UID は Base64URL で区切り文字と分離する。アカウント削除時も、別 UID のキュー・保全コピーは残す。
- 旧版キャッシュの最初の読み取り時には、上書き前の全投稿・返信・評価のスナップショットを
  `legacyTalkBackup.v2.{uid}.{topicId}` に一度だけ保全する。
  `LocalTierStore.loadLegacyTalkBackup(uid, topicId)` で確認・復旧できる。
  旧キャッシュだけでは送信済みかを証明できないため、作者の推定・自動再投稿はしない。
  旧サーバー上の返信は従来どおり表示され、作者不明データは未補完のまま保持される。
- 評価のトグルには端末共通の旧 `_talkReactions` を使わない。
  本人の票を UID 別に読み取り、トランザクションの最新値から同票なら解除、別票なら選択を変更する。
  UI の確定と UID 別キャッシュの更新は成功結果に基づく。
  「A up → B down → A up」は up になり、B の down を誤って解除しない。
- 過去の評価数は履歴の基準値として保持し、新しい UID 別の票だけを加減する。
  昔の数を特定 UID に割り振ったり、端末内の古い選択から減算したりしない。

## アカウント削除の接続

既存の認証・再認証と `deleteAccountData → Authentication 削除` の順序は維持する。
cleanup が失敗した場合は例外が伝播し、Authentication 削除へ進まない。

- 本人が作者の投稿: `recursiveDelete` で投稿と全子文書を削除する。
- 他人の投稿にある本人の新返信・評価: UID のフィールドで検索し、
  `topics/{topic}/talks/{post}/replies|reactions/{id}` に合致する文書だけを削除する。
  同名コレクションが別用途に使われていても、その文書は削除しない。
- 他人の新返信・票、本文、履歴カウンター、作者不明の旧投稿・旧返信は変更しない。
  削除された新返信に他人の返信が付いている場合、その返信は保持され、表示時に親不在の返信として扱う。
- 旧埋め込み返信の本人削除は既存の `replyAuthorIds` / `removeRepliesByAuthor` を維持する。
  投稿を丸ごと消す場合や、旧方式の本人返信の下位ツリーを消す場合の既存の扱いは維持する。
- クライアントからの投稿・返信の直接 delete は禁止する。
  子文書を残して投稿 ID が再利用される経路を作らず、既存の信頼済み削除フローを使う。

エミュレーターテストは固定 demo project を使い、Storage は削除要求を記録するスタブである。
本物の bucket、Authentication ユーザー、実データを削除する処理はテストから呼ばない。

## 検証結果

保留キューの追補では、親削除後の再試行と別投稿操作、先行 write 未完了時の後続返信保存と再起動、
先行 ACK と後続保存の競合、ローカルキューの同時更新を回帰テストに追加した。

- Firestore 実ルール **71 件**とアカウント削除のエミュレーター **5 件**、合計 **76 件成功**。
  UID 別削除、投稿・トピックの子文書削除、405 件のページング、他用途コレクションの保持、
  旧返信と作者不明データの保持、再実行、互換ゲートを含む。
- 既存 Functions テスト **33 件成功**、TypeScript ビルド成功。
- 対象 Flutter テスト **42 件成功**。未確認メール相当の permission-denied 後に再起動し、
  別返信/評価が成功しても本文が残ること、UID を切り替えた再送隔離、2端末の最新票、
  旧キャッシュ保全、別 UID のローカル復旧データの保持、protocol/build 判定を含む。
- 変更対象の Dart 静的解析は指摘なし。
- 追加で画面テスト全体を実行すると **27 件成功・1 件失敗**。
  `widget_test.dart:807` の公開前プレビュー保存テストは、変更のない基点 SHA
  `8cb05ec` の展開済みソースでも同じ `Expected: not null / Actual: null` で失敗した。
  認可修正による回帰とは確認されておらず、このタスクでは無関係な公開処理・テストは変更していない。

再現コマンド（既存 lockfile に従う依存環境と Java 21 / Firestore emulator 1.22.0 が必要）:

```powershell
npm --prefix functions run build
npm --prefix functions test
$env:JAVA_BIN = '<Java 21 の java.exe>'
$env:FIRESTORE_EMULATOR_JAR = '<ローカルの Firestore emulator jar>'
node scripts/test-talk-authorization.mjs
flutter test --no-pub test/talk_activity_test.dart test/talk_write_policy_test.dart test/persistence_and_aggregation_test.dart
```

今回の検証では既存の firebase-admin 14.3.0 / TypeScript キャッシュを読み取り専用で参照して
ビルドし、依存 manifest・lockfile を更新せず同じテストを実行した。
保留キュー追補の実行時にはランナー経由の Java 起動が2回タイムアウトしたため、
同じ固定 demo project のエミュレーターを `127.0.0.1:8789` に直接起動した。
同じ2つのテストモジュールを単一 Node プロセスへ読み込み、76 件の完走を確認した。
検証用エミュレーター以外の既存 Java プロセスには触れていない。

## 残る本人判断

Storage の非公開画像の閲覧範囲、既発行 URL と共有画像コピーの扱いは未決定で、変更していない。
また現方式では、トピックを閲覧できる人は票の UID と選択も読める。
投票者情報を非公開にする仕様が必要なら、ゲート開放前にサーバー集計方式へ変更する判断が必要。
